# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Breaking

- `TZbJson.GetString`, `GetInteger` and `GetBoolean` (in __ZbStructures__) now check the JSON type of the field they read, and raise `Exception` (`ZeroBounce returned the field "<key>" missing or with the wrong JSON type.`) when the field holds another JSON type. With FPC, 3.0.1 converted the value through fpjson: `GetString` returned a number or boolean as its text, `GetInteger` read `true` as `1` and `5.5` as `6`, and `GetBoolean` read a number or a string such as `"true"`. A missing field or `null` still gives `''`, `0` or `False`. Code that calls them on a field of another type, and relied on the conversion, now gets the exception: read the value with `GetValue` and convert it yourself. The signatures are unchanged, so existing code compiles. New: `GetRequiredString` (raises when the field is missing, `null` or not a string) and `GetIntegerText` (the text of a required integer field: a JSON integer as decimal text, or a JSON string returned as it is, unchecked; it raises for a missing, null or other JSON value).

### Added

- `TZbWarmupManagedSending.TimezoneOffsetHours` (`Double`) and `TimezoneOffsetHoursSpecified`, added at the end of the record: hours from UTC with fractional zones such as 5.5 (India) or 5.75 (Nepal). Sent as `timezone_offset` when `TimezoneOffsetHoursSpecified` is set, in place of `TimezoneOffset` if both are set; a whole number is sent as an integer (`"timezone_offset":3`), and a value outside -11.0 to 14.0, NaN or an infinity raises before anything is sent. Like the other `...Specified` flags it must start out `False`: zero the record (`FillChar`, `Default`) before filling it, as the 3.0.x fields already required.
- `TZbBulkParams.RemoveDuplicateSpecified` has no effect: bulk and scoring `sendfile` always send `remove_duplicate` with `RemoveDuplicate` (`false` in a zero-filled record), as 3.0.1 did.
- `TZbBulkParams.ReturnUrl`, last in the record: bulk and scoring `sendfile` send it as `return_url` when it is not empty. A zero-filled record does not send it.
- The plain-http sweep now runs every public request function in a shared list, overloads and the ZbUtility transports included, and a test reads the interfaces of ZbUtility, ZbGeneric, ZbValidation, ZbBulk, ZbPriority3 and ZbWarmup and fails when a public request function is missing from that list. The same list checks that a refused connection raises `ZbException` everywhere.
- `TZbJson.IsNullValue`, `GetOptionalArray`, `GetMessageText`, `ZbRaiseIfNoResult`, `ZbRaiseIfNoFileStatus`, `ZbRequireJsonBody`, `ZbIsStrictJson` and `ZbMessageOnlyBody` in __ZbStructures__. `ZbMessageOnlyBody` is true for `{}` and for a blank, null or list message, as well as for a non-empty string message. `ZbContentStart`, `ZbContentTypeIsHtml`, `ZbContentTypeIsJson`, `TZbDownloadKind`, `ZbDownloadKind`, `ZbStripPadding` and `ZbLastRequestTimeouts` in __ZbUtility__.
- `ZbRegisterSecretRedactor` in __ZbUtility__: adds a function that `RedactSecrets`, and so every `ZbException`, runs over its `Message` and `Payload`. ZbWarmup registers one for the Warmup key and the SMTP credentials of the call in progress.

### Changed

- **Behaviour change:** a base URL that carries a query or a fragment (`https://host/v2?x=1`, `https://host/v2#x`) is refused before anything is sent, with `A base URL must not contain a query string or a fragment ("?" or "#")`. The URL is not included in the message. `https://[::1]/v2` is still a host. Empty brackets are still refused.
- **Behaviour change:** `ZBInitialize`, `ZbWarmupInitialize` and `ZBSetApiKey` refuse a key that holds Unicode whitespace, an invisible character, or a byte that is not valid UTF-8, with `api_key has surrounding whitespace or control characters`. A plain ASCII space in the middle of a key is still sent.
- **Behaviour change:** an HTTP 200 that is only a message (`message`, `Message`, `error`, `error_message`, `Error` or `detail`), or `{}`, or every field that is not a message is null (with or without a message, so `{"Credits":null}` raises), now raises `ZbException` with status 200 on the file upload, delete and status calls, the S3 and SFTP jobs, `ZbSendListEvaluatorFile`, `ZbSendEvaluatedFile`, `ZbBatchValidateEmails`, `ZbActivityData`, `ZbScoreEmail`, `ZbScoreEmailPost`, `ZbGetApiUsage` and `ZbGetCredits`. A string message is the error text. A list of strings is joined with a line feed and used as the error text. Anything else uses `ZeroBounce returned an unexpected JSON response.` A file status with no non-null known field (`{"foo":1}`, `{"message":"m","file_id":null}`) raises. `{"file_status":"Processing"}` and `{"success":true}` stay results. `ZbValidateEmail` still returns a greylist `Message`. The filters, the Inbox Placement calls, and `ZbGetListEvaluatorResult` stay results.
- The package check (`.github/scripts/check-package-versions.sh`) now also fails when a `src/*.pas` unit is missing from `packages/zerobounce.lpk` or `packages/zerobounce.pas` (the `uses` clause and `RegisterUnit`), or a `src/*.inc` is missing from the `.lpk`, and ignores commented-out entries (`//`, `{ }` and `(* *)` in the `.dpk` and `.pas`, `<!-- -->` in the `.lpk` and `.dproj`). `src/zbcasefold.inc` is now listed in `packages/zerobounce.lpk`, like `zboptions.inc`.
- `Dockerfile`: the base image is pinned by digest (`ubuntu:26.04@sha256:...`, the digest the C and C++ SDKs use), and `.github/dependabot.yml` has a `docker` ecosystem so the digest moves with the tag.
- Documentation: README and `documentation.md` state that a timeout of zero or less is refused, the URL character rules and the Warmup download target rules; the README publish steps list every file that carries the version; CONTRIBUTING.md and AGENTS.md say how and when to regenerate `src/zbcasefold.inc`.
- `examples/delphi/ExampleActivityData` (the Delphi twin of the FPC example), listed in `Examples.groupproj` (whose entry pointed at a path outside the repository).

### Deprecated

- `TZbWarmupManagedSending.TimezoneOffset` (`Integer`, whole hours only): use `TimezoneOffsetHours` with `TimezoneOffsetHoursSpecified`. It keeps its type and behaviour and is ignored when `TimezoneOffsetHoursSpecified` is set.

### Fixed

- On Delphi, the JSON POST body, the foreign-key body and the sendfile body were written with `TEncoding.Default`, the Windows ANSI code page, while the JSON POST still said `charset=UTF-8`. They are now written with `TEncoding.UTF8`. The Free Pascal path is unchanged. Delphi was not compiled here.
- `GetInteger` accepted a JSON integer wider than 32 bits and returned the low half, so `{"total":4294967297}` became `1` on `ZbGetApiUsage`. A value outside `Integer` now raises the field-type error. `{"total":1}` is still 1.
- A `processed_at` may separate the date and the time with `T`. `2026-11-17T10:30:00` keeps 10:30:00. The fraction is a decimal of seconds: `.5` is 500 ms, `.12` is 120 and `.592` stays 592. A fraction that is not one, two or three digits is an error. On Free Pascal, an API-usage date (`%d/%d/%d`) starts each part at 0, and a short string such as `11/17` raises instead of becoming a year from the stack. `1/1/2023` still parses.
- A blank `complete_percentage` (`""` or `"%"`) is -1. `"45.5%"` stays 45.5.
- A Warmup download that is not a file raises with the `Http Error:` prefix. If the download directory cannot be created, the call raises `ZbException` (`Could not write <path>`, status 0) and a file already at the path is kept.
- A JSON array used as an error body is reported as `ZeroBounce returned an error response.` A JSON object that carries a string message still uses that text.
- A transport error with an empty payload keeps its message past 299 characters, so the no-CA-bundle instructions (322 characters) are not replaced by an empty HTTP 0 message. `Access violation` is still dropped. A message that copies a non-empty payload is still dropped at 300 characters.
- On Delphi, a validate `processed_at` of `2023-01-12 22:02:02` was read as 1 January: the day was taken from the month. The day is the third field. On Free Pascal, a timestamp with no fraction used an uninitialised millisecond and could raise; every part now starts at 0, so a missing fraction is `.000` and `.592` stays 592.
- On Delphi, a multipart field was split on every `=`, so `return_url=https://cb.example/x?a=1&b=2` was sent as `https://cb.example/x?a`. The value is everything after the first separator. The Free Pascal upload already kept the first `=` only.
- On Delphi, a body that is still gzip (the first two bytes are `1F 8B`) raises `The response from ZeroBounce used a content encoding this client does not read.` A body Delphi has already turned into text is kept. The Free Pascal rule is unchanged: any `Content-Encoding` other than `identity` raises that sentence.
- `ZbGetCredits` on `{"message":"Invalid API key"}` raised the field-type sentence. It now raises that API text with status 200 before the credits field is read. `{"Credits":"-1"}` is still -1.
- `ZbActivityData` took `+5`, ` 5`, `$1F` and `0x10` as a day count. It now accepts only the same integer text as credits (`Json Error: ZeroBounce returned the field "active_in_days" missing or with the wrong JSON type.`, status 200). `{"found":false,"active_in_days":null}` is still -1 and `"12"` is still 12. `{"active_in_days":null}` alone raises, because it has no other field. A JSON integer in the range of `Integer` is that count.
- A finder or domain-search body `{"success":null,"message":"Invalid domain"}` was an empty result, because a null `success` counted as a success field. A null `success` is now absent, so the message raises with status 200 on all of those calls, the deprecated overloads included. `{"domain":null}` with no message stays a result. `{"success":true}` on a file status stays a result.
- `complete_percentage` was parsed with the process locale, so a comma decimal separator rejected `"45.5%"`. It is parsed on a private copy of the format settings whose decimal separator is `.`. The process locale is not changed.
- `ZbValidationFromJson`, `ZbBatchErrorFromJson`, `ZbApiUsageFromJson`, `TZbFindEmailResponseFromJson` and `TZbDomainSearchResponseFromJson`, and the list wrappers in the batch and domain-search parsers, free the `TZbJson` they create. A `TZbJson` the caller passes in is still the caller's.
- `ZbSuccessMeansFailure` used the first `"success"` text anywhere, so a nested `"success":true` hid a top-level `"success":false`. Only the top-level field counts.
- An HTTP error whose body is a JSON object uses a string `message`, `error` or `error_message` as the exception text instead of the raw object. A CSV body (content type `text/csv` or `application/csv`, or at least two lines that each contain a comma) is `ZeroBounce returned an error response.` A JSON body longer than 1000 characters stays that sentence.
- The multipart mock copied the previous response before it set `UrlCalled`, so a sendfile test saw the previous URL. `UrlCalled` is set first.
- `ZbAddFilter` and `ZbDeleteFilter` raise before anything is sent when `Rule` is not exactly `allow` or `block` (`Invalid parameter: rule must be allow or block`) or `Target` is not exactly `email`, `domain`, `mx` or `tld` (`Invalid parameter: target must be email, domain, mx or tld`).
- `ZbCreateInboxPlacementTest` counted the 64-character name cap in UTF-8 bytes, so a 40-character Cyrillic name was refused. It now counts Unicode characters. A 65-character name still raises `Invalid parameter: name must be at most 64 characters`.
- A response whose `Content-Encoding` is anything but `identity` (any letter case, surrounding spaces ignored) is no longer returned or saved. Free Pascal does not decode it, so a gzip body used to come back as the file, and any `Content-Encoding` skipped the cut-short check. Every FPC request now raises `ZbException` (`The response from ZeroBounce used a content encoding this client does not read.`, status 0) and a Warmup file already at the path is kept. `identity` still uses the cut-short check.
- On Delphi, `ZbWarmupDownloadSeeds` and `ZbWarmupDownloadStatistics` wrote `Length(Content)` bytes of a UTF-16 string, half the file with a zero byte between letters. They now write the UTF-8 bytes. The FPC build is unchanged.
- A failed replace of a Warmup download raised `EWriteError`. It now raises `ZbException` (`Could not write <path>`, status 0). The temporary file is still removed and the file already at the path is kept.
- A short API message that contained `<`, such as `Invalid email <a@b.c>`, was replaced by the raw body. It is kept. A message of 300 characters or more, and `Access violation`, are still dropped. A JSON body longer than 1000 characters is reported as `ZeroBounce returned an error response.`
- A download no longer treats an HTML page as the file when white space, a byte-order mark or a no-break space push the tag past the first 2000 characters. `ZbBulkValidationResultFetch`, `ZbAiScoringResultFetch`, `ZbEmailFinderResultFetch`, `ZbDomainSearchResultFetch`, `ZbWarmupDownloadSeeds` and `ZbWarmupDownloadStatistics` skip that padding, then look at 2000 characters. A body of only that padding is an error. A file that really begins with white space is still saved unchanged. `<head` does not match `<header>`. A `<html`, `<head` or `<body` tag anywhere in those 2000 characters is HTML, including one inside the file.
- A JSON error behind a byte-order mark or a no-break space, or a JSON array, was saved as the file by the four getfile calls. After the same padding skip, `{` or `[` is an error on all six downloads. The content type is compared in any letter case: `application/json`, anything ending in `+json`, and `text/json`, so `Application/JSON` is an error even when the body is a JSON string.
- `ZbBatchValidateEmails` raised the account-level `"all"` error with status 0 and an empty `Payload`. It now raises from the response: status 200, the body kept, the key masked.
- On Windows, `ZbWarmupDownloadSeeds` and `ZbWarmupDownloadStatistics` deleted an existing file before renaming the temporary file over it, and the Delphi branch never took that path because it defines `MSWINDOWS`, not `WINDOWS`. The finished file is now moved into place in one step (`MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` and `MOVEFILE_WRITE_THROUGH`), so a failed move leaves the old file.
- A finder or domain-search answer whose only key is a message key (`error`, `message`, `error_message`, `Message`, `Error` or `detail`) is now an error with status 200 whatever the message is. 3.0.1 read a blank, `null` or list message as an empty result (`ZbFindEmailByDomain`, `ZbFindEmailByCompanyName`, `ZbDomainSearchByDomain`, `ZbDomainSearchByCompanyName`); a non-blank text was already an error. A list message's text is joined with a line feed in the error. `{}` and a message beside fields that are all null (`{"message":"Invalid domain","domain":null}`) are the same error, including on the deprecated overloads. A string message is the error text; with no message text the error is `ZeroBounce returned an unexpected JSON response.` `{"domain":null}` with no message stays a result.
- A `null` or missing `start_date` or `end_date` in the usage answer (`ZbGetApiUsage`) reads as no date (0). 3.0.1 raised on both (`Invalid date/timestamp`).
- A `null` or missing `complete_percentage` in the file status answer reads as -1, the value a blank one gives. 3.0.1 raised on both.
- `null` in an optional list field is read as the empty list, as the other SDKs read it: `email_batch`, `errors` and `other_domain_formats` (`null` or missing) used to raise "Field ... not found" with status 200, on `ZbBatchValidateEmails` and the domain search. A `null` or missing `upload_date` on the file status calls is no date (`0`) instead of an `Invalid date/timestamp` error with status 200 (3.0.1 raised on both).
- The `message` of a file job (`ZbBulkValidationFileSubmit` and the other submit and delete calls) may be a list of strings, as the API sends it on a failed upload: the list is joined with a line feed (`#10`) instead of raising with status 200. A string message is unchanged.
- Typed calls took an HTTP 200 JSON object whose fields were missing, null or of another JSON type as a result, coercing or defaulting them: `ZbGetCredits` returned `0` for `{}` or `{"Credits":null}` (those now raise `Http Error: ZeroBounce returned an unexpected JSON response.`), `1` for `{"Credits":true}`, and `6` for `{"Credits":5.5}`; `ZbValidateEmail` returned `'5'` as the address for `{"address":5,...}` and `'7'` as the status for `{"status":7}`, and a result with no address or status at all for `{}`; any string field took a number or boolean as text, and an integer field took `true` or `5.5`. Field types are now part of the response shape: such a body raises `ZbException` with the HTTP status (200) (`Json Error: ZeroBounce returned the field "<name>" missing or with the wrong JSON type.`). `Credits` is an integer within the range of `Integer`, sent as a JSON string (`"-1"`, `"12345"`) or as a JSON integer (`{"Credits":2375323}`, zerobounce.net's own example, read as in 3.0.1); `"5.0"`, `"abc"`, `5.5`, `1e3` or `2147483648` raises. `ZbScoreEmail` and `ZbScoreEmailPost` take a `score` that is an integer or the string form of one: 3.0.1 read `5.5` as `5` and `" 9"` as `9`, and both now raise; a `null` score leaves `HasScore` `False` when some other field is not null. `{"score":null}` alone raises `Http Error: ZeroBounce returned an unexpected JSON response.` `ZbValidateEmail` (and each `ZbBatchValidateEmails` row) needs `address` and `status` as strings, except a greylist answer that carries its text in `Message`, which is still a result. `null` is still accepted for every optional field, and the documented example responses still parse. Warmup and the raw-JSON calls are unchanged.
- A chunked download cut mid-stream came back as the whole result: fphttpclient stops reading a chunked body when the connection closes and reports nothing, so `ZbBulkValidationResultFetch` returned the 34 bytes that had arrived as the file. Every request now notes when the server closed the connection, and a chunked body that ends that way, before its last (empty) chunk, raises `ZbException` ("cut short") with status 0, on every transport and download (Warmup CSV included).
- `ZbBulkValidationResultFetch`, `ZbAiScoringResultFetch`, `ZbEmailFinderResultFetch` and `ZbDomainSearchResultFetch` returned `HasContent = True` for an empty HTTP 200 body, and for an HTML page whose body did not look like HTML (a proxy's `<p>Access denied by proxy</p>` sent as `text/html`). Both now raise `ZbException` with the status; a `text/html` content type is checked in any letter case.
- An answer cut short was returned as the result on the JSON POST (`ZbBatchValidateEmails`), form POST (`ZbValidateEmail` with `UsePost`, `ZbScoreEmailPost`, the S3/SFTP jobs, filters, `ZbSendEvaluatedFile`) and multipart upload (`ZbBulkValidationFileSubmit`, `ZbAiScoringFileSubmit`, `ZbSendEmailFinderFile`, `ZbSendDomainSearchFile`, `ZbSendListEvaluatorFile`) requests: when the connection closed before the `Content-Length` the server promised, whatever had arrived was parsed, and if it parsed it came back as a success. With FPC these requests now raise `ZbException` (`The response from ZeroBounce was cut short: N of M bytes received`, `StatusCode` 0), as GET requests and the Warmup and Inbox Placement Tester requests have since 3.0.1. The Delphi branch is unchanged.
- An upload whose connection was refused raised `ZbException` with an uninitialised `StatusCode` (any number, for example `-599851432`). It is now 0, like every other error with no HTTP answer.
- A request that got no HTTP answer (connection refused or timed out, a TLS or protocol failure) raised fphttpclient's own exception instead of the `ZbException` the README tells callers to catch: `ESocketError` (for example `Connect to 127.0.0.1:1 failed.`) or `EHTTPClient`, with no `StatusCode`, from every GET request (`ZbGetCredits`, `ZbValidateEmail`, the file status, result and delete calls, the email finder and domain search, the list evaluator and more), the JSON POST (`ZbBatchValidateEmails`), the form POSTs (`ZbValidateEmail` with `UsePost`, `ZbScoreEmailPost`, the S3/SFTP jobs, the filters, `ZbSendEvaluatedFile`) and `ZBSendRequest` / `ZBSendRequestWithHeader` / `ZBSendForeignKeyRequest` (the Inbox Placement Tester). They now raise `ZbException` with `StatusCode` 0 and the original message, with the API key masked as `REDACTED`, as uploads and the Warmup API already did. The Delphi branch gets the same wrapping (its multipart upload too), but it is not compiled in CI.
- **Behaviour change:** the Inbox Placement Tester calls returned an empty string as the result for an empty 2xx body, whatever the call. Only `ZbDeleteInboxPlacementTest` answers with an empty body, so it alone still does; an empty 2xx from `ZbInboxPlacementProviders`, `ZbInboxPlacementTestTypes`, `ZbCreateInboxPlacementTest`, `ZbInboxPlacementTest`, `ZbListInboxPlacementTests`, `ZbInboxPlacementWebhook` or `ZbSetInboxPlacementWebhook` now raises a `ZbException` (`Http Error: Empty response from ZeroBounce (HTTP 200)`) with `StatusCode` set to the HTTP status.
- `ZbWarmupDownloadSeeds` and `ZbWarmupDownloadStatistics` returned (and saved to `DownloadPath`) an answer that is not a CSV file when its content type did not say JSON: a JSON object or array under `text/csv` (`{"message": "..."}`), or a `text/html` page. They now raise `ZbException` with the status for an empty body, a JSON or HTML content type, or a body that is a JSON object or array, and save nothing.
- `ZbWarmupDownloadSeeds` and `ZbWarmupDownloadStatistics` with a `DownloadPath` opened the path with `fmCreate` and wrote into it, so a write that failed part-way (a full disk, a file size limit) raised but destroyed a file that was already there and left the partial one in its place. They now write to a temporary file `.<uuid>.zbtmp` in the target's directory and move it into place only when the whole file is written; a failed write removes the temporary file and raises, and the earlier file is kept unchanged. The file keeps the permission bits of the file it replaces.
- An HTTP 200 labelled `text/html` whose body parsed as JSON (a proxy's or a captive portal's page, `{"a":1}`) came back as the result of every JSON call (validation, scoring, the email finder and domain search, the bulk status calls, the filters, the S3/SFTP jobs, the Inbox Placement Tester, every Warmup JSON call); only an HTML-looking body raised. A `text/html` content type (in any letter case) now raises `ZbException` with the HTTP status on every request.
- The raw-JSON calls (`ZbAddFilter`, `ZbListFilters`, `ZbDeleteFilter`, `ZbGetListEvaluatorResult`, `ZbListS3Files`, the Inbox Placement Tester calls) and every Warmup JSON call returned an HTTP 200 body that is not JSON as their result: a proxy's `hello` as `text/plain`, `not json` or a CSV labelled `application/json`. They now raise a `ZbException` with `StatusCode` 200 (`Json Error: ...`), as the parsed calls already did. An empty 200 is still the documented empty success of the Warmup calls and of `ZbDeleteInboxPlacementTest`; from the other raw-JSON calls it now raises with its status too.
- A JSON body followed by other text on an HTTP 200 (`{"a":1} <- proxy note`) was read as its leading JSON value, because fpjson's `GetJSON` stops after the first value: every JSON call returned it as the result. Every JSON call now raises a `ZbException` with the status for a body that is anything but one JSON object or array (whitespace around it allowed).
- Every JSON call (the typed results, the raw-JSON calls such as the filters, the list evaluator, `ZbListS3Files` and Inbox Placement, and every Warmup JSON call) took bodies that are not JSON as the result, because fpjson's `GetJSON` is lenient: single quotes (`{'a':1}`), unquoted keys, `TRUE`, leading zeros (`01`) and a raw tab in a string. A 2xx body must now be one strict RFC 8259 JSON value with only space, tab, CR or LF around it, checked on the body as it came; anything else is a `ZbException` with status 200. A JSON string or number on its own (`"x"`, `0`) is JSON too: the raw-JSON calls return it. A typed call (every call that returns a record or an integer) now raises a `ZbException` with status 200 for any JSON value that is not an object (`0`, `"x"`, `true`, `null`, `[]`) rather than reading it as an object with no fields. Only a zero-byte Warmup 2xx (or HTTP 204) stays the documented empty success, as does a zero-byte `ZbDeleteInboxPlacementTest`; a body of only whitespace is a `ZbException` with its status.
- **Behaviour change:** a `success` field that is not a real flag no longer switches the error checks off. A flag is a JSON boolean, the number 0 or 1 (`1.0` too), or the text `true`, `false`, `0`, `1` in any case (ASCII whitespace trimmed). Before, any non-null `success` (`2`, `0.4`, `"maybe"`, `0`, an object) made `getapiusage`, `activity`, `score`, the finder and domain search, `validatebatch`, the filters, Inbox Placement types and the Warmup statistics and list calls skip the error-key, message-only and no-result checks, so `{"success":0,"message":"Invalid file id"}` and `{"success":"maybe","error":"Invalid API key"}` came back as a result. Now such a field is read as if it were absent (it neither counts as a result nor as success), and a real false (`false`, `"false"`, `0`, `0.0`, `"0"`) is a failure in every spelling.
- **Behaviour change:** a typed file-feedback or file-status answer whose `success` is `1`, `"true"` or `"1"` now reads as success (it raised a field-type error before); a `success` of any other non-flag type still raises it.
- **Behaviour change:** the error text of a JSON object is its `message`/`error`/`error_message` field even when the body is longer than 1000 characters (before: the fixed "ZeroBounce returned an error response."). The fixed sentence is kept for an object with no such field, or a field itself longer than 1000 characters. A JSON list on an error status (`["Invalid key"]`) now keeps its text (first 1000 characters, secrets masked); on a success status it is still read as "a file's place" with the fixed sentence.
- **Behaviour change:** `ZbReadTimeoutMs` or `ZbConnectTimeoutMs` of 0 or less is refused before any request with "ZbReadTimeoutMs must be greater than 0" / "ZbConnectTimeoutMs must be greater than 0". Before, 0 could wait forever and a negative value failed only when the request was made.
- Masking is linear in the length of the text: every spelling of the secret is found in one pass and the result is built once, so a mask is never scanned again and masking an already masked message leaves it unchanged. A match that overlaps the `REDACTED` text the masker writes is masked together with it. Decoded views (URL, form, JSON, HTML entities; up to four layers) cover the whole body; the decoders are linear and a layer that cannot change the text is skipped. A 2.8 MB ordinary error body is masked in well under a second; one made only of decoder triggers (`%`, `+`, `&`, `\`, non-ASCII) takes a few seconds.
- **Behaviour change:** the Warmup CSV downloads (`ZbWarmupDownloadSeeds`, `ZbWarmupDownloadStatistics` with a path) refuse a target that cannot be a file before anything is sent: a last component that is empty (a trailing separator), `.` or `..`, or a path that names an existing directory. Before, the request went out first and a trailing separator created the directory. The error is `Could not write <path>`. The parent directory is still created only when there is a file to write, after the request succeeded.
- **Behaviour change:** a download whose target is a symbolic link is written through to the file the link points to (the whole chain is followed) and the link stays a link. Before, the link was replaced by a regular file. A chain of more than 40 links, or a cycle, raises `Could not write <path>: too many levels of symbolic links` and leaves the link untouched. Not resolved on Windows.
- **Behaviour change:** `ZbWarmupTestSmtpConfiguration` sends the SMTP username and password exactly as given; before, both were trimmed, so a password with a leading or trailing space was altered. An empty or blank value is still refused. The redaction masks the values as given.
- Delphi: a response whose Content-Encoding is not empty or `identity`, or whose bytes received differ from its Content-Length, raises a ZbException with StatusCode 0 (as FPC already did); the gzip magic-byte check is kept as well. (Written against System.Net.HttpClient; not compiled here.)
- A multipart upload's transport error (connection refused, timeout, TLS) now has the same text shape and StatusCode 0 as the other calls (the library's message, key masked), instead of an "Http Error:" prefix.
- A JSON list error body over 1000 characters on an error status gets the fixed text "ZeroBounce returned an error response." instead of being cut at 1000 bytes (which could split a UTF-8 character).
- **Behaviour change:** `ZbValidateEmail` on a 2xx message-only answer (`message`, `error`, `error_message`, `Error`, `detail`, alone or beside nulls) raises with that message's text (key masked) and the response status, instead of the field-type text. The greylist answer (non-blank `Message`) stays a result.

### Security

- Redaction compares text under Unicode 16.0.0 canonical normalization and full case folding: NFD(casefold(NFD(x))) with the canonical ordering of combining marks, from tables generated by `tools/gen_casefold.py` (`src/zbcasefold.inc`) and `tools/gen_normalize.py` (`src/zbnormalize.inc`); Hangul syllables are decomposed algorithmically. An echo of a secret in another case or normalization form is masked: `ß` as `SS`, a ligature spelled out, final sigma, the Kelvin sign, Hangul against its jamo, polytonic Greek, and a Turkish upper-casing of an ASCII key (`İ`, `ı` and `i` + U+0307 fold to a plain `i`). 3.0.1 masked only the key exactly as given and its URL-encoded form. Combining marks are kept, so a secret is not masked inside a longer accented letter. A key with no base character (only combining marks) is refused with `api_key has surrounding whitespace or control characters`, and the previous key is kept.
- Named character references used when searching for a secret now include the HTML 4 Latin-1 names (`&eacute;`, `&nbsp;`) and the ASCII punctuation names (`&lpar;`, `&period;`, `&NewLine;`, `&Tab;`). A numeric reference may omit its semicolon when the next character is not a digit. `%u0027` is still not decoded.
- `ZbLastRequestBody` and `ZbLastRequestHeader` are per thread. `ZbLastRequestMethod` is cleared at the start of a request and then set to the method that request uses, so a refused URL does not keep the previous method.
- On Free Pascal for Unix, linking the SDK links `cwstring`. Without it, an HTTP 200 JSON error that quotes a non-ASCII key came back with the accent replaced by `?` and the key left in the exception message. The test program does not link `cwstring` itself.
- On Delphi, percent-decoding, `\x` and octal escapes assemble UTF-8 bytes instead of one UTF-16 unit per byte, and a code point above U+FFFF is a surrogate pair. The Free Pascal path already held UTF-8 bytes.
- A key containing U+0600–U+0605, U+06DD, U+070F, U+0890, U+0891, U+08E2, U+110BD, U+110CD, U+13430–U+1343F or U+13447–U+13455 is refused with `api_key has surrounding whitespace or control characters`, and the key already set is kept.
- `ZbLastRequestBody` and `ZbLastRequestHeader` are recorded only while a mock response is installed, and only by `ZBSendForeignKeyRequest` and `ZBFormPostRequest`. Every request function clears them before it checks the URL, so a refused URL does not keep the body or header of an earlier mock, and a request with no mock does not leave a key or an SMTP password in those variables.
- Redaction ignored letter case, so an upper-cased echo of the API key, the Warmup key, the SMTP username or the SMTP password was returned in `Message` and `Payload`. Matching now folds case, including `ß` echoed as `SS`.
- A secret containing `'` echoed as `\'`, `\x27`, `\x{27}`, `\47`, `\u{27}`, `\U{27}`, `\U0027`, `\U00000027` or octal `\047`, or a secret echoed through a numeric character reference (`&#39;`, `&#x27;`, `&#x0027;`, `&#34;`, `&#233;` and the same with any letter case or leading zeros), `&quot;`, `&gt;`, `&apos;`, `&amp;` or `&lt;`, was returned. Those spellings are now decoded when searching for the secret, and the body is dropped for `The response body was omitted because it contained a credential.` `%u0027` is not treated as an encoding.
- The API key, the Warmup key and the SMTP username and password of `ZbWarmupTestSmtpConfiguration` were masked raw (and the keys URL-encoded) only, so an answer that quoted them JSON-escaped, as a server or proxy echoing the request body would (`Pa\/ss\"w%rd`), or the SMTP credentials URL-encoded, left them readable in `ZbException.Message` and `Payload`. Every secret is now masked raw, URL-encoded (a space as `%20` or `+`, and as `EncodeParam` puts it on a query string), JSON-escaped (`/` escaped or not), JSON-escaped twice (an echoed body quoted inside another JSON string, `Pa\\\/ss\\\"w%rd`) and URL-encoded after JSON escaping (`Pa%5C%2Fss%5C%22w%25rd`, as a server putting an echoed JSON body into a URL or form would), through the new `ZbMaskSecret`.
- `ZbException.Payload` held the response body unredacted: a body quoting the API key, such as `{"error": "Invalid API key <key>"}` or `{"success": false, "message": "... <key>"}` on an HTTP 200, or a 4xx quoting the request URL with `api_key=<key>`, handed the key to any caller that read `Payload`, on every call. Only `Message` was masked. Every `ZbException` now has the key, raw and url-encoded, replaced by `REDACTED` in both `Message` and `Payload`, whatever built it (an API error body, an account-level `ZbBatchValidateEmails` error, a transport error). The Warmup functions also mask the Warmup key in its url-encoded form, not only raw.
- A Warmup CSV download that got a JSON answer quoting the Warmup key, such as `{"message": "Invalid API-Key <key>"}` on an HTTP 200, raised a `ZbException` with the key in both `Message` and `Payload`: the error was raised after the request, outside the only place that masked the Warmup key, and `ZbException` itself masked only the validation key. Every `ZbException` now masks the Warmup key (raw and url-encoded) and the SMTP username and password of `ZbWarmupTestSmtpConfiguration` in `Message` and `Payload`, whatever raised it.
- Key and SMTP-credential redaction covered only the spellings `ZbMaskSecret` generates (raw, URL-encoded, JSON-escaped and a few compositions), so a body quoting a secret through another composition, such as URL-encoded three times, reached the exception's `Message` or `Payload` decodable. After masking, the text is now decoded up to four more times (`ZB_SECRET_DECODE_LAYERS`: the SDK's own request encoding plus three layers an echo may add; URL-decoding with upper- or lower-case hex, `+` as a space, JSON-unescaping including `\/`, `\uXXXX` and surrogate pairs, in any order; a `%00` or `\u0000` does not end the search); if any view still holds the API key, the Warmup key or the SMTP username or password, the whole text is replaced by `ZB_SECRET_OMITTED_MESSAGE` ("The response body was omitted because it contained a credential.").
- **Behaviour change:** every URL the SDK sends to (the Main API base, `BULK_URI`, `ZbBulkRootURL`, `ZbListEvaluatorURL`, `ZbInboxPlacementURL`, `ZbWarmupBaseURL`, and `ZBInitialize(key, baseUrl)`) is refused before anything is sent if it contains a control character (CR, LF, tab, C1), DEL, any Unicode white space (space, NBSP, U+2000-U+200A, U+3000 ...), an invisible or bidirectional format character (U+200B-U+200F, U+2060, U+FEFF, U+202A-U+202E, U+2066-U+2069 ...), a backslash, invalid UTF-8, or a non-ASCII character in the host. Before, a CRLF in a base URL could inject raw request headers and surrounding white space was trimmed silently; now a leading or trailing space is refused too. The message is "<name> must not contain a backslash, whitespace, control or invisible characters, invalid UTF-8, or a non-ASCII character in the host". The existing user-info, query and fragment refusals are unchanged.
- The previous API key buffer is overwritten with zeros when `ZBInitialize` / `ZBSetApiKey` replace it, and the key is wiped at unit finalization (only when the SDK holds the sole reference to the buffer). New public `ZbWipeString(var S)` for other units.
- The Warmup API key, the SMTP credentials kept for redaction while a test-smtp call runs, and the request body that carried them are overwritten with zeros when replaced and at unit finalization (the SDK keeps a private copy of the key so the buffer is its own to wipe).
- A Warmup download's temporary file is created with its final permission bits (those of the file it replaces, or the default creation mode for a new file) before any data is written, so its content is never more readable than the target's. New: `ZbWarmupTempCreatedHook`, a test seam (nil in normal use) called once the temporary file exists and before the first write.
- **Behaviour change:** a multipart upload (the bulk and AI-scoring file calls) refuses a CR, LF or NUL in any form value, field name or the file name before sending ("The value of the form field "return_url" must not contain a line break or a NUL character"; the value is not quoted). Before, a `return_url` holding a line break and the boundary could add a form part of the caller's choosing.
- The multipart boundary is random per request (`ZbForm` + the hex of two GUIDs) and regenerated if it occurs in the file or a value, on FPC and Delphi. Before, FPC used a fixed boundary, so a CSV containing it broke the body.
- A `%` in the host or port of a URL is refused (`https://api.zerobounce.net%40evil.com/v2`); `%XX` stays allowed in the path.

### Changed

- **Breaking:** `ZbApiKey` and `ZbApiBaseURL` are per thread (`threadvar`). In 2.1.3 they were global, so an app that calls `ZBInitialize` on the main thread and makes requests from worker threads now gets `ZeroBounce is not initialized. Please call ZBInitialize(api_key) first` on those threads. Call `ZBInitialize` on each thread that makes requests.
- **Breaking:** `BULK_URI` is now a typed variable instead of a constant, so tests can point it at a local stub. Code that uses it in a constant expression (`const MyUrl = BULK_URI + '/sendfile';`) no longer compiles; use a variable or the new `BULK_HOST` constant (`'bulkapi.zerobounce.net'`).
- **Breaking:** FPC builds now verify the server's TLS certificate and host name (2.1.3 did not verify at all), which needs trusted CA certificates. They come from `ZbCACertFile`, else the `SSL_CERT_FILE` environment variable, else (not on Windows) the usual Unix bundle paths (`/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/ca-bundle.pem`, `/etc/ssl/cert.pem`), else `cacert.pem` beside the executable, else - on Windows only - the Windows "ROOT" system certificate store. When none of these yields a certificate, every request raises a `ZbException` saying how to provide one, and a `ZbCACertFile` or `SSL_CERT_FILE` that names a missing file raises rather than falling back. Verification is never switched off. To supply a bundle yourself, download one (for example https://curl.se/ca/cacert.pem) and either save it as `cacert.pem` beside the executable or set `ZbCACertFile := 'C:\path\to\cacert.pem';` before the first request. Delphi builds use the operating system's TLS stack and are unaffected.
- `ZbException.Message` is now just the error, with the key redacted. In 2.1.3 it was the message followed by `Url:`, the URL (key included), `Status code:` and `Payload:` blocks; read `ZbException.StatusCode` and `ZbException.Payload` instead, which are unchanged. On an HTTP error the message is the API's own (a JSON error body as sent, or a non-JSON body with a repeated `Error:` / `[Error]:` prefix removed), prefixed with `Http Error: `, for GETs, JSON and form POSTs alike. FPC builds raise a `ZbException` carrying the status for every HTTP error; in 2.1.3 a GET with any status other than 200 raised fphttpclient's `EHTTPClient` ("Unexpected response status code") instead.
- `ZBInitialize` raises a `ZbException` when the key has surrounding whitespace or control characters, instead of sending it.
- **Breaking** for code that checked the returned record: a `"success": false` field on an HTTP 200 now raises instead of being returned as a result, with `ZbException.StatusCode` 200. `getfile` and `deletefile` report an unknown or deleted file id that way. This applies to every request path - GET, JSON POST, multipart upload and form POST.
- A redirect (HTTP 3xx) raises `ZbException` ("ZeroBounce returned a redirect, which this client does not follow.") instead of being followed, so the key cannot be sent on to another host. This is new for Delphi, whose `THTTPClient` followed redirects in 2.1.3; FPC builds already raised on one.
- API requests have a 30-second connect timeout and a 120-second read timeout (FPC: `ConnectTimeout` / `IOTimeout`; Delphi: `ConnectionTimeout` / `ResponseTimeout`). 2.1.3 set none.
- Query values, including the API key and email address, are percent-encoded.
- The standalone example `examples/delphi-api-v2/ValidateEmailExample.dpr` uses Delphi's `System.Net.HttpClient` instead of Indy (`IdHTTP`/`IdSSLOpenSSL`), so it needs Delphi XE8 or later but no OpenSSL DLLs, and it no longer builds with Free Pascal. Its README and the root README now say so. The SDK itself is unaffected.

### Fixed

- An invalid or drained API key now raises a `ZbException` carrying the API's message, with `StatusCode` 200. The API answers one with an HTTP 200 and no `success` field: `{"error": "Invalid API key or your account ran out of credits"}` from validate and activity, `{"error": "Invalid API key"}` from getapiusage, and `{"Message": ...}` from the email finder and domain search. In 2.1.3 `ZbValidateEmail` and `ZbGetApiUsage` raised a misleading `Json Error: Invalid date/timestamp ...`, `ZbDomainSearchByDomain` and `ZbDomainSearchByCompanyName` raised `Json Error: Field "other_domain_formats" not found ...`, `ZbFindEmailByDomain` and `ZbFindEmailByCompanyName` returned a result with an empty email, and `ZbActivityData` returned -1. `message`, `Message` and `detail` decide failure only for the email finder and domain search, because successful responses use them too (a repeated `greylist_processing` validate answers `{"Message": "Greylist validation still in progress. Please try again later."}`, which is a result). `ZbGetCredits` still returns -1 for an invalid key, as documented.
- `ZbFindEmailByDomain` and `ZbFindEmailByCompanyName` omit `first_name` when it is empty. Both appended `&first_name=` unconditionally, so the overloads that pass `''` for the names they do not take sent a blank field. The deprecated `ZbFindEmail` had always guarded it.
- The api-usage response now reads `sub_status_leading_period_removed` and `sub_status_alias_address`, two counters the API returns that were silently discarded.
- A validation response without `processed_at` no longer raises. A greylist retry that is still running answers with `Message` and no date; `ProcessedAt` is left at zero instead.
- A 403 HTML "Access denied" page is raised as a short error. An HTML page with status 200 is an error as well, including bulk `getfile`, instead of file content.
- An HTTP error status (400 and above) whose body is empty or not JSON raises a short message, with a repeated `Error:` / `[Error]:` prefix removed. An empty body on HTTP 200 raises `Empty response from ZeroBounce (HTTP 200)`; any other non-JSON body on HTTP 200 still raises a `Json Error` with the JSON parser's message (the body is on `Payload`).
- `ZbBatchValidateEmails` raises when the batch has an account-level error (HTTP 200, error for address `all`, such as an invalid API key or no credits). An error for one address stays on the returned batch.
- `ZbBatchValidateEmails` sends an empty IP address as JSON `null`, and escapes the email, IP and key for JSON.
- Requests are not sent when `ZBInitialize` was given an empty API key.
- The domain search examples (`examples/fpc/ExampleDomainSearch.lpr`, `examples/delphi/ExampleDomainSearch.dpr`) compile. Since 2.0.0 they have called `ZbDomainSearchByDomain('example.com', 'John', 'Doe')`, but the function takes only the domain; they now pass the domain alone and print the format and confidence the API returns. CI now compiles every FPC example.

### Security

- FPC builds verify TLS certificates and host names (see the CA-bundle entry under Changed); 2.1.3 accepted any certificate, so the `api_key` in request URLs could be read by a man in the middle.
- Plain `http://` is accepted only for an exact loopback host, and a URL with user information is refused, so neither `ZBInitialize` nor a hand-set base URL can send the key to another host over plain HTTP (`http://localhost.evil.example`, `http://127.0.0.1@evil.example`).
- Redirects are not followed, so the key is never forwarded to another host.
- Query parameters are percent-encoded, so a value cannot rewrite the request URL.
- Exception messages no longer include the request URL (which carries the key) or the raw HTML access-denied page. The response body remains on `ZbException.Payload`.
